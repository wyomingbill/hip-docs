## 0. Executive summary

The demo player already has the right architecture: an operator-paced, server-side state machine (`scripts/demo_run.py`) that fires each scripted turn through the real `process_text_query()` and lets the dashboard panes react by polling real logs. Three findings shape this spec:

1. **AUTO-RUN mostly exists.** A server-side autonomous runner (`run_script()`, `demo_run.py:97–159`, exposed at `POST /api/demo/start`, `demo_dashboard.py:766–791`) already plays a script hands-free through `process_text_query` with per-turn `pause_ms * pause_scale`. The demo console UI never calls it. AUTO-RUN is therefore primarily a UI-wiring and pacing-polish task, not new engine work.
2. **The richest governance renderer is starved.** The `/epistemic` page (epistemic.html) can render deny-reason codes, EMPTY-SET GUARD banners, STATE TRANSITION delta strips, and a live trust ramp — but its data source (`logs/turns_demo.jsonl`) is written **only** by `scripts/text_demo.py` (`text_demo.py:209–212`), never by the demo player path. Meanwhile the demo page's own Epistemic Timeline renders only fact chains + trust badges — no deny reasons, no guard banners, no park/confirm UI (verified absent from demo.html). The core structural fix of this spec is a single shared **epistemic record writer** in the engine path so every mode (manual, auto, voice) feeds every pane.
3. **Voice rides the same governed path but doesn't log to the demo surface.** `realtime_adapter.py` calls `assemble_governed_context` (adapter :301–302) — same assembly as the text path — but only at `connect()`, and writes neither `log_turn_metadata` nor `write_transcript_turn`, so the panes stay dark during a voice session. The `OrchestratorGate._on_user_text` path (voice_orch.py:1269+) already does all the per-turn logging (metadata :1525, governed assembly :1598 per BUILD-1). VOICE mode = per-turn logging parity in the adapter (or routing voice through the gate), plus the shared epistemic writer.

## 2. Gap analysis

**G-1 (structural, blocks everything rich): no engine-side epistemic record.**
The demo player fires `process_text_query`, which logs turn metadata (`injected_fact_ids`, `guard_triggered`, tier, bloom) but **not** the admitted/withheld/deny-reason/delta record the `/epistemic` renderer needs. That record exists only in `text_demo.py` (:157–204), which builds it by running a **second** decide + injection-contract pass (:132–135) and its own `_deny_reason` replay (:42–71) — a shadow reimplementation that can drift from the real contract. The fix is to emit the epistemic record from inside the single real pass (see D-1).

**G-2: demo page timeline can't show refusals or transitions.** Deny reasons, guard banners, delta strips, park/confirm are renderable only on `/epistemic`, which the operator isn't looking at during a demo. Cards for HARDEN/RESOLVE/CONFIRM exist in the HOW IT WORKS overlay marked "BUILT · NOT WIRED LIVE" (demo.html:1300).

**G-3: AUTO-RUN has no UI, no beat-dwelling.** `run_script` sleeps a flat `pause_ms * pause_scale`; it does not know that turn R04 (a P8 park) deserves a longer dwell than R01 (a routing one-liner), and the client's 700ms answer stagger + 1s timeline trail are tuned for manual pacing.

**G-4: voice writes nothing the panes read.** No `log_turn_metadata`, no `write_transcript_turn` in the adapter; governed context assembled once at connect rather than per turn (stale after any fact write mid-session — a correctness gap, not just a display gap).

**G-5: the five-rung ladder is seeded but not exercised live.** Seed D1–D9 statically covers all rungs, but no current script makes a rung **move** on screen: no scripted corroboration climb, and the P8 park → P10 confirm pair is only accidentally captured (reveal_demo R04's expected file records an unconfirmed-update hold as *observed* behavior, not as a narrated beat).

**G-6: vault reveal is disconnected from the narrative.** The KD-step animation fires on tab click any time; no script beat directs the operator (or auto-run) to it at the moment a fact was just written/decrypted.

**G-7 (security, pre-existing, TD-101 part 2): `POST /api/decrypt` is unauthenticated** (`demo_dashboard.py:187–199`) — any client can decrypt any owner's ciphertext. The demo's per-member reveal is UI theater over an open endpoint. In-scope here only as a constraint: the demo spec must not deepen the dependency on unauthenticated decrypt, and the TD-101 fix must not break the reveal.

**G-8 (cosmetic): `_expected.json` files pollute the script dropdown** (`demo_dashboard.py:672`); confirmation replies ("yes") must come from the bound actor with exact vocab (`confirmation_gate.py:51–58, 132–137`) — scripts must encode the confirming member correctly or P10 beats will silently no-op.

## 3. Design decisions (apply to all three modes)

**D-1 — Single epistemic record writer in the engine path.**
Extract the record-building logic of `text_demo.py` (:157–204) into a shared module (working name `harness/epistemic_record.py`) that takes the **already-computed** `InjectionResult` from the single real `apply_injection_contract` pass inside `assemble_governed_context` — no second pass, no predicate replay. Requirements:
- The engine emits deny reasons natively: extend `InjectionResult` (injection_contract.py:183–201) to carry a per-withheld-fact reason code at the point each `_inj*` rule denies (:379–406), replacing `text_demo.py:_deny_reason`.
- `process_text_query` appends the record to `logs/turns_demo.jsonl` after its existing `log_turn_metadata` call (:2805–2820); same for `OrchestratorGate._on_user_text` (voice path) after :1525.
- Record schema = the existing `text_demo.py` schema (turn_id, ts, member, query, reply, tier, complexity, intent, bloom, net, admitted[], withheld[] with reason codes, guard_triggered, delta[] with cause_utterance) so `/epistemic` renders it unchanged, plus new fields: `park` (P8 park event: parked_fact_id, head_fact_id, rungs) and `confirmation` (P10 resolve/decline event).
- `text_demo.py` becomes a thin CLI wrapper over the same path (Phase-B-style consume; do not delete it until the wrapper is proven).
- Session filtering: records carry `ts`; `/api/turns` grows a `since=` param (mirroring `/api/transcript`) so the demo session filter works.

**D-2 — Governance Feed pane on the demo page.**
Add the `/epistemic` turn-card renderer (admitted/withheld columns, deny codes, guard banners, delta strips, trust ramp — epistemic.html:401–613) to `demo.html` as a fourth zone (or replace/augment the current TimelineZone), fed by `/api/turns?since=<sessionStart>`, gated on the same `conversationSettled + 1s` trail as the current timeline (demo.html:601–624). The existing fact-chain timeline stays — chains show *state*, turn cards show *why*. This un-orphans "BUILT · NOT WIRED LIVE."

**D-3 — Beat annotations in the script schema (v3).**
Add optional per-turn fields, backward compatible with v1/v2:
- `beat`: enum naming the governance beat (`routing | retrieval | write | supersede | corroborate | park | confirm | decline | empty_set | cross_member_refusal | injection_attempt | household | vault_reveal`) — drives narration overlays and auto-run dwell.
- `dwell_ms`: auto-run hold time after the panes settle for this turn (overrides the flat `pause_ms`).
- `focus`: which pane the UI should highlight/glow for this beat (`conversation | routing | timeline | governance | vault:<member>`); `vault:<member>` auto-triggers the KD reveal for that member's tab (fixes G-6 — reveal becomes a narrated beat, not dead filler).
- `narrate`: on-screen caption (already exists in v1 as `note`/`narrate`; formalize).
Loader (`demo_run.load_script` :84–94) accepts version "3"; layer2 expected-file mechanism extends unchanged (sha-pinned).

**D-4 — Every displayed state must be engine-produced.** No pane may render a governance state that did not come from the real `InjectionResult`, real `encode()` write-state, real trust classification, or real router decision. The only permitted theater: pacing, highlighting, and the KD-step animation (which visualizes a real HKDF derivation but does not perform it client-side).

### Stage 2 — AUTO-RUN

**2a. ### Stage 3 — VOICE

Target state with known imperfections, but end-to-end real.

**3a. Per-turn logging parity in the voice path.** Two options, decided at implementation time by which path the demo voice session actually uses:
- If sessions run through `OrchestratorGate` (voice_orch.py:1269+): it already logs metadata (:1525) and transcripts (:1638–1727); only the Stage-1 epistemic writer hook (1a) is needed. **Preferred.**
- If through `RealtimeAdapter` directly: add per-turn `build_turn_metadata`/`log_turn_metadata` + `write_transcript_turn` mirroring voice_orch.py:2790–2820, **and** re-assemble governed context per turn (or on every fact write) instead of once at connect (:301–302) — the stale-context gap is a correctness fix required regardless of the demo.
**3b. Demo surface for voice:** a VOICE mode toggle on `/demo` that (i) stamps a `session_start` without loading a script (new lightweight `POST /api/demo/voice-session`), (ii) shows the live member identity from speaker verification, (iii) lets all panes react to spoken turns exactly as to scripted ones. No script, no NEXT — the panes are the show.
**3c. The voice demo story** (operator cue card, not code): speak a fact write, hear the governed answer, watch routing + vault; switch speaker (or use the second voiceprint) and ask a cross-member question → hear the refusal, watch `deny_default_cross_member` land in the Governance Feed. Known imperfections to acknowledge in the run report: STT variance can miss the exact P10 confirm vocab (`confirmation_gate.py:51–58` is exact-match by design); voiceprint verification quality with seeded synthetic prints (demo_seed.py:144–158) must be validated with real audio before showing speaker switching.
**3d. Verification:** VOICE-GOV suite still green (source conformance, eval/harnesslib/voice_governance_conformance.py); a recorded voice session producing correct records in all four logs (router, transcript, turn_metadata, turns_demo); cross-member voice refusal reproduced live.

## 5. Acceptance criteria (whole system)

1. Every rung of `TRUST_RANK` (trust.py:27–32) is visibly exercised in at least one script, with the rung transition rendered (delta strip or timeline chain), engine-produced.
2. P8 park and P10 confirm **and** decline each appear as narrated beats with the parked/UNRESOLVED state visible while parked.
3. All four deny codes render live in the Governance Feed during `privacy_guards`.
4. Operator/member/household encryption reveal occurs as a directed beat in `vault_reveal`; no mode depends on new unauthenticated surface (G-7 constraint).
5. Routing pane shows at least: three on-net tiers, one off-net escalation, one sensitivity-blocked fallback.
6. AUTO-RUN plays any v3 script hands-free with no beat advanced before its panes settle.
7. VOICE session drives all panes through the same governed path, cross-member refusal included.
8. All scripts sha-pinned with expected files in the L2 gate; epistemic-writer conformance case in the harness; no regression in existing L1–L5 / VOICE-GOV / SIA gates.
9. Zero simulated states: every badge, banner, strip, and refusal traceable to `InjectionResult`, `encode()`, trust classification, or `RouteDecision`.

## 6. Risks / open questions

- **R-1:** In-turn corroboration (harden) may require running consolidation mid-script; if latency is prohibitive, the `trust_ladder` script pre-seeds the harden and narrates it from the seeded state (weaker but honest). Decide in Stage 1c.
- **R-2:** Extending `InjectionResult` touches `injection_contract.py` — gate with the full guard-mutation layer (L3) and the existing INJ conformance before any push.
- **R-3:** `/api/demo/start` autonomous path is legacy and untested against the current status-file consumers; Stage 2 must re-validate the `running` state against the client's state chip mapping (demo.html:674–680).
- **R-4:** Voice Stage 3 depends on which transport the demo actually uses (Gate vs RealtimeAdapter); spec deliberately defers that decision to first implementation session with live audio.
- **R-5:** TD-101 part 2 (auth on `/api/decrypt`) lands independently; coordinate so the vault reveal keeps working (likely a demo-session token).
