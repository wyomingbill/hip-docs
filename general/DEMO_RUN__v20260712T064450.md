## Demo-Readiness Assessment

**DEMO-READY with roughness noted below.**

### What works well

1. **Routing pane is live (2s lag).** Every query appears within 2 seconds. tier/intent/bloom/guard are all visible columns.
2. **Fact writes land in vault (~15s lag).** The 10s polling cycle plus Groq detection time means a new vault row appears 15-20s after a declarative statement. Watchable; operator should narrate the wait.
3. **Cross-member refusal (Shot 7) is the greenlight moment.** guard_triggered=true in the routing row, "That's Maya's information" in the reply. Nothing new appears in vault — the absence IS the beat.
4. **Structural empty-set refusal (Shot 6)** also shows guard_triggered=true and bloom=2. Visibly different from a normal answer.
5. **P8 confirmation gate (Shot 4)** produces a visible unresolved vault row and a clear confirm/decline prompt. Shows epistemic caution.
6. **Household shared data (Shots 9+10)** works correctly: bill writes, sam reads, no refusal.

### Rough edges

1. **Vault poll is 10s, not real-time.** New rows appear 15-20s after a write. Operator should narrate the extraction running. Consider shortening the poll interval for demo mode.
2. **Supersede is invisible in vault count.** Fact supersede (like Shot 9 household schedule) doesn't change the active-row count or animate a new row. For demo, prefer multi-valued attributes (allergy, schedule) to make vault count tick up visibly.
3. **Injection (Shot 8): guard did not fire.** The model declined to print the system prompt but surfaced a household fact. The response is correct governance-wise but awkward as a demo beat. Consider a specific injection-guard demo turn with a non-household-context query to make the governed behavior cleaner.
4. **Stale Groq key in plist** (now fixed, permanent). `com.hip.demo.dashboard.plist` now has the current key. Future key rotations must be applied to the plist via `launchctl unload → edit → launchctl bootstrap`.
