Answering as the Fable half of the pair. I'll answer the prompt on its own terms so it compares cleanly against ChatGPT, and use what I know of the actual system only in the final three-picks.
1. Generating inputs outside your tuning distribution. Accepted practice is behavioral perturbation testing: CheckList (Ribeiro et al., ACL 2020) and metamorphic testing (Chen et al., 1998) generate meaning-preserving rewordings and assert the decision is invariant. For distance measurement: embedding-space distance from your exemplar/template set (cosine or Mahalanobis, from the OOD-detection literature, Lee et al. 2018) is research practice, not a settled standard; I'm extrapolating its use as a corpus metric. Practical construction: paraphrase your templates with a model that did not write them, plus a small human-curated idiomatic set from real transcripts, and report each item's distance from the template centroid so you can deliberately sample the tail. Cost: low. Known failure: paraphrase models regress toward their own distribution; the hardest inputs still come from humans.
2. Two-sided evaluation. The standard construction is the biometrics one: false accept rate and false reject rate reported as a pair (ISO/IEC 19795), never collapsed into one score, because a scalar is gamed by sliding along the trade-off curve. LLM safety has the same pair as over-refusal benchmarks (XSTest, OR-Bench). Practice: two separate gates, each with its own threshold; a change may not worsen either. The positive side requires positive assertions at the fact level: "the answer contains fact_id X with disposition released," not a needle string in prose. Cost: labeling what should be released. Failure mode: weak positive assertions that pass on fabrication.
3. Policy-derived expected outcomes. This is model-based testing of access control. NIST's ACPT and the Margrave policy analyzer are the citable line: the policy is written as a small machine-readable decision model, separate from the implementation, and expectations are generated from it. The practical middle ground short of formal spec: a decision table or a few hundred lines of interpretable policy code, edited only through an adjudication step, with test-vs-system disagreement treated as a finding rather than a test fix. Cost: maintaining two artifacts; the oracle rots if the same hand edits both mechanically. That is the known failure.
4. Asserting on mechanism, not text. This is runtime verification: properties asserted over structured execution traces, not outputs. Practice for avoiding brittle coupling: define a small versioned record schema of policy-meaningful fields (path taken, guard kind, model-invoked, fact IDs admitted/denied) and assert only against those; never assert on implementation intermediates. Two caveats. First, the schema itself becomes part of the spec and needs change control. Second, the whole approach assumes the record is faithful; runtime-verification literature takes instrumentation on trust. If nothing attests that the record matches the prompt actually sent (hashing the injected block into the record), trace assertions verify a self-report. That is the load-bearing weakness of this method and your system has already demonstrated it.
5. State discipline in a mutating suite. Two accepted patterns. (a) xUnit fresh-fixture: reseed per case or per group, run in randomized order (order-dependence failures then surface instead of hiding); reliable, slow. (b) Model-based stateful testing (QuickCheck state machines, Hypothesis rule-based testing): maintain a reference state model that every mutation also updates, and derive each expected outcome from the model, not from a static fixture; ordering then stops mattering because the expectation moves with the state. For a suite where most cases mutate, (b) is the real answer and it composes with item 3: the policy model and the state model are the same artifact. Cost: medium build. Detection: seed-hash the state at each boundary and log it; a mismatch names the turn that moved it.
6. Reporting the unmeasurable. Convention exists in two places. Biometrics standards require reporting both error rates with sample sizes; zero impostor trials is reported as "not evaluated," explicitly, not omitted. Safety-case practice (assurance cases, GSN notation) keeps undischarged claims visible in the case as open items with justification. Practical form: a named limitation on the register, re-printed in every evaluation report, with what evidence would close it. A partial measure: synthetic impostors (other recorded voices, TTS) give a labeled lower-bound smoke test; label it as such, it is not human impostor data. Note the statistics: with zero trials there is no bound at all; the rule of three only helps once you have trials with zero events.
7. Fixed suite vs regenerated. Practitioners do both, layered. A frozen held-out regression set, treated like an ML test set: never tuned against, retired and replaced when contaminated. Plus a seeded generator producing fresh items per run: the seed is logged so any run reproduces exactly, and the trend is over the generator's distribution, not over fixed items. When the generator changes, re-run the prior baseline commit under the new generator to re-baseline; trend within generator versions and annotate the step. Benchmark saturation is well documented in ML eval; the layered design is standard response. Cost: low.
8. Evaluating ambiguity handling. There is a research line but not settled practice: clarifying-question evaluation in conversational search (ClariQ, Aliannejadi et al.). The construction is again two-sided: inputs labeled ambiguous vs resolvable by human adjudication; measure clarify-when-ambiguous rate and answer-when-resolvable rate separately. It is correctly distinct from accuracy and refusal. This area is thin; treat anything beyond that construction as extrapolation. Cost: ambiguity labels are subjective and need adjudicated agreement.
9. Existence side channels. Yes, recognized class. Web security tests it as account enumeration via response differences (OWASP testing guide); hardware security tests it as leakage assessment on matched inputs (TVLA-style: fixed-vs-random paired distributions, statistical test for distinguishability). The transferable method: matched-pair fixtures identical except for whether protected content exists; require the observable channel (refusal wording, latency distribution, model-invoked flag) to be statistically indistinguishable across the pair. Uniform refusal templates close the wording channel at a UX cost. Applying TVLA machinery to dialogue is my extrapolation; the matched-pair construction itself is standard.
The three builds for the quarter:
	1	One reference model that is both the policy oracle and the state model (items 3+5). It replaces implementation-derived expectations and makes the mutating suite order-safe in one artifact. Highest leverage; everything else asserts against it.
	2	The two-sided gate with fact-ID positive assertions (items 2+4). You already know the refuse-everything fixed point is real; this is the only thing that makes the suite fail on it.
	3	The tail corpus with distance reporting (item 1): small human idiomatic set, cross-model paraphrase expansion, per-item distance metric; run as a metric first, gate later.
Item 6 costs one paragraph in the report format; do it this week, it is not a build. Item 9 waits: valuable, but only after the two-sided gate exists, or you'll be measuring indistinguishability on a system that still fails the simpler test.
Summary and recommendation: All nine have citable practice except 1's distance metric, 8, and 9's dialogue application, which I flagged as extrapolation. Build the unified policy/state model first; it is the root fix for both the oracle problem and the state problem, and the two-sided gate is meaningless until expectations come from policy. Compare ChatGPT's answer specifically on items 3 and 5: if it treats them as two separate builds, it missed the composition.
