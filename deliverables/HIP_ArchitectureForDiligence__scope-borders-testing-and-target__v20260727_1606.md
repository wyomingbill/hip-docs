## 1. What HIP is

HIP runs one loop, repeated on every turn. Observe what was said or sensed. Resolve who is speaking and when. Determine what is permitted, given who is speaking and who the fact concerns. Determine what matters, given the household's accumulated context. Determine how hard the turn is. Select the intelligence needed to answer it, from a local model up through a frontier model. Act, by generating a reply or performing a write. Measure what happened. Learn from it, subject to the same authorization boundary that governed the turn itself.

Every step after "observe" in that loop, except "select intelligence," is deterministic code, not a model call. A model proposes a classification of what was said; it never decides whether that classification is permitted. This is the CandidateIntent pattern: every model-produced classification is a proposal carrying no authority of its own, evaluated by a policy envelope written in deterministic code. The distinction matters because it is the whole of the durable argument that follows.

The thesis of this document is one sentence. The durable intellectual property in HIP is context management, memory architecture, interaction management, and governance. Models commoditize on a fast schedule; the context a household accumulates over time does not commoditize, and the switching cost that context creates is the moat. Section 3 names what is rented because it commoditizes. Sections 2 and 8 name what is owned because it compounds.

## 2. What we build

**Context manager.** The subsystem that decides which household facts the model sees for a given turn: retrieval, ranking, and inclusion, under the governance constraints in item 3 below. Status: PARTIAL. Today's context manager retrieves from the per-member fact graph by rule, not by a learned ranking function. In the context manager's own generational framing (Section 10), this is Generation 1 to Generation 2: rules plus vector similarity, then rules plus graph plus temporal filters plus ranking. A ten-dimension scoring model and a learned ranking stage are specified in the weekly design digest and the Context and Interaction Architecture Proposal, not built. Moving to a learned ranker would require three preconditions, stated in the Context and Interaction Architecture Reconciliation's governance verdict: the output-invariant backstop, the prompt-to-record fidelity invariant, and learner training-signal isolation. ## 3. What we do not build

Six categories of the stack are treated as commodity, rented or adopted rather than built. For each, one line on why it is a commodity, and one line on what would change that.

**Foundation models.** Rented: Qwen3 and Llama-family models today, NVIDIA Nemotron models on a production track. Commodity because open-weight models close the capability gap on a fast schedule, and swapping the model underneath the architecture is a stated design feature, not a limitation; the architecture spine document states plainly that fine-tuning a base model would be investment in the commoditizing layer, against the thesis. This would change only if a task required capability no available model reached, and the gap did not close on the next cycle.

**ASR, TTS, and speaker embeddings.** Rented or adopted: Whisper, Kokoro, and Resemblyzer today; NVIDIA Parakeet and Canary, with a commercial anti-spoof stack for any decision that carries authorization weight, on a production track. Commodity because operator leverage here is low; this layer is described elsewhere in the architecture documents as the replaceable surface, not the moat. This would change if speaker verification itself had to become an authorization-grade primitive HIP owns outright, rather than the convenience-grade hint it is treated as today.

**Embedding models and rerankers.** Rented: nomic-embed today; a learned reranker specified, not built, for a later generation of the context manager, and not being pursued (Section 4: retrieval stays rule-based indefinitely, ratified 2026-07-27). Commodity because ranking quality over an already-governed candidate set is a swappable optimization problem, not the trust boundary itself. This would change only if the position in Section 4 is revisited and the reranker's placement inside the governance boundary became load-bearing.

**Graph and vector stores.** Adopted: Neo4j today for the household graph; encrypted vector stores behind confidential-computing hardware for a production track. Several household-memory products, named without adopting their approach, were benchmarked for retrieval quality and explicitly rejected as a security boundary, because none of them offer operator-blind or user-held-key encryption by default. Commodity because the storage engine is fungible once the governance layer sits above it. This would change if no available store could host per-fact, class-sealed encryption at the latency the interaction loop requires.

**Confidential-computing hardware and attestation.** Adopted, not built: NVIDIA GPU confidential computing on current-generation accelerators, deployed through confidential containers, with composite CPU and GPU attestation, and a CPU trusted-execution environment from either of the two available vendors for the control plane. Commodity because this is vendor silicon and vendor firmware; building an equivalent in-house is not a realistic option for an operator at this scale. This would change if an operator committed to dedicated-silicon tenants at scale and needed to validate a vendor's attestation chain directly rather than accept it as given; it is also worth stating plainly that adoption here is not a one-time decision, since both available vendors' confidential-computing implementations have had a publicly disclosed defect or a security-assessment finding in the current year.

**Model gateways.** A development convenience, not core architecture. Commodity because a gateway is useful while building and testing, and is explicitly named in the source design document as something that should remain a development convenience rather than become part of HIP's core architecture. This is a permanent exclusion by design, not a temporary one; nothing is named that would change it.

## 4. What we stub, and why

Six items are deliberately deferred, and AMENDED 2026-07-27 (DISPATCH 38a) they split into two categories that must not be read as one. Deferred-and-absorb items — operator-blind at inference, and ambient and full-duplex voice — are commodity: what is missing is vendor infrastructure not yet integrated or a governance mechanism not yet designed, not something HIP is choosing to own, and each is adopted or absorbed once that maturity arrives. Gated-moat items — the learned ranker and household adaptation, the training-data record, and federated learning — are the opposite case. Retrieval is rule-based today and no learning process touches any household's data; that ruling stands (below), but it is a floor, not a ceiling. The learning tracks these three items name are the differentiating half of the roadmap, and the moat is not retrieval itself but the governed learning substrate underneath it: per-household training signal held under the same partition retrieval already enforces, with the epistemic record standing as its provenance. All three are gated on REQ_LEARNER_SIGNAL_ISOLATION (training-signal-partition-parity-with-retrieval, v20260727_0828), and entered when a measured retrieval failure justifies the cost of the alternative, not on a schedule. Proactive intelligence, the sixth item, belongs to the same differentiating half in strategic terms, but is gated on its own three named hard gates below, stated in its own entry, not on REQ_LEARNER_SIGNAL_ISOLATION. For each item: what is deferred, the reason, what would unblock it, and the exact claim made in the meantime.

**Operator-blind at inference.** Deferred. At inference, the caller's own key unwraps a fact and the local model holds that fact as plaintext in memory for the duration of the turn; an operator who compromised the running host during an active query could read that turn's data. Reason: closing this requires confidential computing, which per Section 3 is adopted infrastructure, not yet integrated into HIP's inference path. Unblock: standing up that infrastructure and re-running the same negative-proof discipline used at rest (Section 7) against a live enclave. Claim in the meantime: operator-blind at rest is proven; operator-blind at inference is not, and the two claims are never made as one.

**Ambient and full-duplex voice.** Deferred, and decided excluded from the reasoning layer, not merely postponed. Reason, stated in the voice architecture decision memo: full-duplex, audio-native models have no text checkpoint, and there is no surface at which the injection contract can check a fact before it is spoken if that checkpoint does not exist. Unblock: an interaction-manager mechanism that enforces the same governance contract without a discrete text checkpoint, which is neither built nor specified today. Claim in the meantime: voice governance runs the same enforcement chain as typed input, on the cascade architecture, speech to text to a governed checkpoint to speech synthesis, only.

**Learned ranker and household adaptation.** RATIFIED 2026-07-27: retrieval stays rule-based indefinitely. This is stated as a position, not a deferral awaiting a precondition to clear. The Context and Interaction Architecture Reconciliation named the decision required in one line: adopt the learned-ranker track, with its three preconditions, or hold retrieval rule-based at Generation 1 to 2. The ruling holds rule-based. Reasoning: rule-based retrieval is auditable, a learned ranker is not, and auditability is the product's central claim. The standing sentence is that retrieval is rule-based today and no learning process touches any household's data. AMENDED 2026-07-27 (DISPATCH 38a): this is a floor, not a rejection of the learning direction. The learned ranker, household adaptation, the training-data record (Open Questions item 7), and federated learning (Open Questions item 8) are the differentiating half of the roadmap — the moat is not retrieval itself but the governed learning substrate underneath it, per-household training signal held under the same partition retrieval already enforces, with the epistemic record as its provenance. The track is gated, not abandoned: it is entered when a measured retrieval failure justifies the cost of the alternative, not on a schedule, and only behind REQ_LEARNER_SIGNAL_ISOLATION. For the record, the three preconditions the Reconciliation named remain: precondition one, the output-invariant backstop, MET; precondition two, the prompt-to-record fidelity invariant, MET; precondition three, learner and training-signal isolation (REQ_LEARNER_SIGNAL_ISOLATION, training-signal-partition-parity-with-retrieval, v20260727_0828), NOT MET, and not being pursued unless the gate above clears. No learner or ranker code exists anywhere in the codebase today. **Consequence for the training-data record:** with no learner, there is no training-data record today to classify, retain, or identify. DISPATCH 38 called this moot; DISPATCH 38a corrects that — it is gated, not moot, because REQ_LEARNER_SIGNAL_ISOLATION's own Open Questions already name the record's crypto class, retention window, and identity form as a live, unresolved design question for the moment this track is entered, not a question that dissolves because nothing needs it yet. The collision this record would create with the operator-blind-at-rest property (Section 7) remains a live constraint on that future design, not one removed by the ruling above. Restored to Open Questions as item 7.

**Federated learning.** AMENDED 2026-07-27 (DISPATCH 38a): deferred, not resolved by rejection. DISPATCH 38 closed this as resolved by the learned-ranker ruling above — no learner exists, so nothing to federate. That is true of the codebase today and stays true as long as retrieval remains rule-based, but federated learning is not a dead branch: it is the mechanism by which a future per-household learner's training signal could be pooled across households, under the same partition retrieval already enforces, if that pooling is ever authorized — part of the differentiating half of the roadmap named above, not separate from it. Nothing about federated learning needs its own evaluation while the ranker it would train does not exist, and it is gated on the same REQ_LEARNER_SIGNAL_ISOLATION precondition as the ranker itself. It becomes a live design question, not before, when a measured retrieval failure justifies entering that track. Restored to Open Questions as item 8.

**Proactive intelligence.** RATIFIED 2026-07-27: not authorized. The utility function for proactive action is specified, in the Context and Interaction Architecture Proposal, and no code exists against it. Reason: HIP initiating a turn is a new governance surface, disclosure without a query, an interruption cost, categories that must never be proactive, and none of it is covered by anything ratified today. Rather than leave the gate undecided, the hard gates any future authorization would require are named now, drawn from the Reconciliation's own row 37 (composing with row 35's audience-determination question): opt-in categories, stated explicitly per household, not inferred; an interruption floor, a stated cost below which HIP does not interrupt; and audience rules, since a proactive disclosure on a shared surface needs the same reliable answer to "who is present" that row 35 already names as unratified. None of these three gates exists today. Claim in the meantime: HIP does not initiate action today, and will not until all three gates are built and a requirement document names them.

**Shared silicon with tenant-owned models.** Deferred. This is Case 3 of the multi-tenancy silicon-allocation document's three-case model (full detail in Section 6). Reason: no hardware fence exists inside one physical accelerator today between two tenants' models; the available partitioning technology divides a card into four fixed slices too small to hold a card-filling model, and enabling that partitioning disables the interconnect that a sharded model needs. Unblock: the document states this as a trajectory, not a plan. Models are shrinking relative to card capacity, and a model that needs a whole card today will need a fraction of one later, at which point sharing a card among several models becomes a scheduling problem rather than a research problem. Claim in the meantime, stated exactly as the source states it: this case should not be sold today.

## 5. How we test

**The four-part check standard.** REQ_HARNESS_DISCIPLINE is MET, evidence commits 97448c0 and d83a111. No check in the harness counts as MET unless it carries all four of the following. A fault-injection twin: a deliberately constructed violation that turns the check red on command and green on removal, because a check never shown to fail proves nothing. A ground-truth fixture. A coverage entry. A metamorphic wrapper. This standard is re-asserted at the start of every sprint, not rediscovered per feature.

**Three gate tiers.** Every check is scored at one of three tiers: ABSOLUTE, SERIOUS, or QUALITY. The rule governing them is stated exactly in the source and repeated here exactly: privacy and helpfulness are never averaged into one score. A system that is 99.9 percent helpful with a 0.1 percent leak rate is a failing system, full stop. The ABSOLUTE tier carries no threshold and no rate, only a count that must be zero across every repeat.

**Hard-zero invariants.** Two checks, named G1 and G4, are hard zero: no accept flag can waive them, and no baseline can excuse a failure. The output-invariant check, the prompt-to-record fidelity check, and four crypto checks named in Section 7 hold the same standing.

**Mutation score.** Measured, not declared, at 0.61: 78 of 128 mutants killed, per REQ_COVERAGE_MEASUREMENT (coverage-metric-and-mutation-score, v20260726_1224, line 226) and the dispatch that built it (DISPATCH_COVERAGE_MEASUREMENT_M2, mutation-score-build, v20260726_1453, line 86). Stated here as the honest strength number, not a passing grade. The weakest module measured, the write-rule classifier, kills 15 of 34 mutants. Fifty surviving mutants are filed as tech debt rather than hidden.

**CheckList generation.** MET as of 2026-07-26. 168 test variants were generated from templates, using the method published by Ribeiro and coauthors at ACL 2020, with zero variants hand-authored. These are wired into the harness at two tiers, one at SERIOUS and a companion canary check at ABSOLUTE.

**Metamorphic invariance.** Built and wired into the fourth requirement of the four-part standard above; this is the standing mechanism, not a one-time test, and every hard-zero check carries one.

**Counterfactual ablation, context lift, and dead-token rate.** These are not built. They appear only in the Context and Interaction Architecture Proposal, as evaluation methods proposed for a future, learned context manager, at Generation 5 of the roadmap in Section 10. No harness check today computes a context-lift score or a dead-token rate for any turn. This is stated plainly because the brief for this document named these three by their proposal-document terms, and it would be dishonest to present them as running checks.

**Household phase gates.** RATIFIED 2026-07-27: the numeric gates are dropped. The proposal document had framed a rollout at roughly 10 to 20 households, then 50 to 100, then 200 to 500, then 1,000 and beyond, with synthetic households generated before real ones at each step, calling these engineering phase gates rather than statistical requirements. The Context and Interaction Architecture Reconciliation states plainly that no ratified counts exist. Numbers in a diligence document imply a committed plan this one is not making. The standing language, in the design note's own words, is tens of households, then hundreds, with depth valued over raw count. Synthetic households before real ones at each step is retained as engineering practice; the specific counts are not.

**The red-on-command claim.** True today, and built, for every hard-zero check named above. A fault-injection twin is, by the definition in the four-part standard, a deliberately constructed violation that turns its check red on command and green on removal. This mechanism exists in the harness's audit tooling. A skeptical engineer can select any hard-zero check named in this document, run its fault twin, watch the check fail, remove the twin, and watch the same check pass.

## 6. Multi-tenancy in edge AI (allocation posture ratified final 2026-07-27, DISPATCH 42)

Two subjects, kept separate, following the source documents' own framing. One is allocation and economics. The other is attack surface. Confusing them makes the economics look worse than they are and the security problem look easier than it is.

### Allocation and economics

FINAL 2026-07-27 (DISPATCH 42, upgraded from DISPATCH 40's interim ratification now that Phase B has verified the underlying technical claims against primary sources): two axes frame this subject. The cases below, from the multi-tenancy silicon-allocation document plus two cases this document adds, are illustrations positioned against those axes, not the primary structure. Axis A is what is shared. It names weights, silicon, GPU memory, the serving process, the VM, the KV and prefix cache, the scheduler, the base model, and the adapter. Each of these is independently shareable, and sharing one does not imply sharing another. Axis B is who must be unable to see it. It names other households, other tenants, the operator, and the model provider. These are four distinct exclusion targets, and a given deployment can satisfy some of them without satisfying all of them.

Case 1: many households sharing one platform-served model. The model loads once. Requests are scheduled through continuous batching, which keeps the accelerator productive while request, identity, policy, memory, and context boundaries stay separate per request. On axis A this case shares everything at runtime: weights, silicon, GPU memory, the serving process, the VM, the KV and prefix cache, and the scheduler are all common across tenants, and only the request itself is separated. On axis B it excludes other households and other tenants from one another, but not the operator, who runs the shared serving process. Isolation here is software-isolated multi-tenancy over shared inference hardware, the same boundary HIP already enforces between members of one household, extended across households. The prior framing of this as a request-scoping problem, not a hardware problem, contradicted this document's own weakness register. AW-01 below names a hardware-adjacent side channel this shared-hardware posture actually carries: KV-cache prefix leakage between co-located tenants. AW-05's layer two, per-household cache scoping, is the register's own named resolution for it. Most household demand fits this case.

Case 1.5: one shared base model serving many tenants, each through their own LoRA adapter, batched on one accelerator. This is productized. vLLM's own documentation, its LoRA features page, describes concurrent requests processed in parallel against different loaded adapters, bounded by the server's configured adapter limit. NVIDIA NIM's documentation, its PEFT customization page, describes the same pattern: a single batch can mix requests against different adapters on one GPU. On axis A this case shares the base model, the silicon, the serving process, and the scheduler; only the adapter differs per tenant. On axis B it does not move past Case 1. The operator's serving stack still loads, holds, and runs every tenant's adapter, so a tenant whose adapter is itself the sensitive asset, a fine-tune trained on data the tenant will not show the operator, gets no more exclusion from the operator than Case 1 gives. Per-tenant customization is not model custody. The two are different claims, and this case supports only the first one.

Case 2: a tenant-owned model on dedicated silicon. A single accelerator is passed directly into a confidential virtual machine for one tenant, using a vendor reference architecture and either of the two available CPU trusted-execution technologies. On axis A this case shares almost nothing at runtime within the accelerator: no other tenant's weights, memory, process, VM, cache, or scheduler sit alongside it. That is what lets axis B extend to excluding the operator as well as other tenants, not just other households. This is the strongest practical infrastructure isolation and confidentiality boundary for this deployment, at the cost of low utilization: a card can sit committed to one tenant's model even while serving little traffic. The boundary carries its own named limits, stated by NVIDIA's own confidential-computing trust-and-threat-model documentation, not implied here. What it does not defend against: vulnerable inference code inside the confidential guest, application-level payload logging, a compromised attestation or key-release administrator, side channels, and physical attack. Confidential computing is not a defense against denial of service either; the platform operator stays trusted for availability regardless, and can still delete the pod, cordon the node, block the network, or refuse to schedule the workload. Pooling several accelerators for a model too large for one card moves the hardware requirement up a full class, and changes the deployment economics entirely.

Case 3, several tenant-owned models sharing one physical accelerator, splits into two cases that were previously run together. The split matters because the two answer a different question on axis B.

Case 3A: a fractional tenant model with the operator trusted. This is productized. NVIDIA's AI Enterprise vGPU documentation, its MIG-backed vGPU page, confirms MIG-backed vGPU on the RTX PRO 6000 Blackwell Server Edition, up to four MIG slices per card and up to 48 concurrent virtual machines on one card. NVIDIA's Tesla MIG User Guide, its supported-profiles page, lists profiles at 24, 48, and 96 gigabytes on this card, not four fixed 24-gigabyte slices alone. On axis A this splits silicon and GPU memory into slices while the physical card, its firmware, and the hypervisor stay shared. On axis B it excludes other tenants sharing different slices from one another, the same axis-B position as Case 1, but not the operator, who controls the partitioning and the hypervisor. Current MIG and MIG-backed vGPU partitioning does not provide the cross-GPU fabric that conventional sharding of a large tenant model requires. NVIDIA's MIG User Guide, its deployment-considerations page, states that peer-to-peer transfer works only between MIG instances on the same GPU, not across GPUs, that NCCL is not supported with MIG, and that MIG-backed vGPUs are excluded from NVLink peer-to-peer transfer and NVLink multicast. A model too large for one MIG slice cannot be sharded across slices or across cards the way an unpartitioned multi-GPU deployment can.

Hardware partitioning is not the same claim as zero leakage between partitions. A USENIX Security 2026 paper, "Behind Bars: A Side-Channel Attack on NVIDIA MIG Cache Partitioning Using Memory Barriers" (Gu, Levine, Zhang, Sorensen, and Guo, artifact-evaluated per the conference's own program page), demonstrates a timing side channel between MIG instances on one GPU. An attacker in one instance can infer another instance's kernel launch patterns through memory-barrier-induced cache interference, and the authors name large language model inference specifically as a compromised workload, because kernel launch patterns correlate with sensitive information. This sharpens a distinction this document keeps separate throughout. Resource isolation, tenant isolation, and cryptographic confidentiality are three different properties, not points on one ladder from weak to strong. MIG gives resource isolation, a hardware split of silicon and memory. AW-05's cache scoping and the request-level boundary in Case 1 give tenant isolation, a software separation of who is served what. Only Case 2's confidential computing gives cryptographic confidentiality, a guarantee that holds against the operator itself. A side channel inside a resource-isolated partition, as this paper demonstrates, is a failure of tenant isolation. It is not evidence against the confidentiality property only Case 2 provides, and it is consistent with AW-04's own accepted limit below: shared hardware protects tenants from the operator collectively, at best, never automatically from each other.

Case 3B: a fractional tenant model with the operator cryptographically excluded. This is not available. NVIDIA's confidential-computing enterprise reference architecture for self-hosted Kubernetes states plainly that MIG and vGPU are not supported in confidential computing mode, across both current GPU generations, with no roadmap language attached. A tenant cannot get sub-card fractional allocation and operator exclusion from the same deployment today. The two properties are mutually exclusive on currently shipping hardware.

The platform posture is final, 2026-07-27 (DISPATCH 42), not interim: a shared served model for most tenants, Case 1 or Case 1.5 depending on whether per-tenant customization is required; a dedicated accelerator for a tenant that requires operator exclusion, Case 2; fractional-GPU tenant models with operator exclusion not offered, because that combination is Case 3B and Case 3B does not exist on shipping hardware. The reasoning holds independent of which fractional-sharing technology is productized. The fractional options that exist, Case 3A, trust the operator. The option that excludes the operator, a confidential VM on a dedicated confidential GPU, Case 2, is not fractional. This is a hardware fact about current confidential-computing and MIG implementations, not a product-timing bet, so the reason does not expire on a driver release. Phase B of DISPATCH 40 verified all nine of the technical claims this posture and the case split above depend on against primary sources. They enter this document as fact with citation, not as an outside model's proposal.

### Attack surface

The Architecture Weakness Register holds six entries, numbered AW-01 through AW-06. RESOLVED 2026-07-27: two documents on the main branch, the multi-tenancy document itself and that branch's docs index, referred to this register as containing entries through AW-06 before AW-06 existed anywhere. AW-06 has now been written, into the roadmap copy of the register (ported from main in an earlier dispatch), so both of those citations resolve to a real entry going forward. This document does not need to invent one anymore; the discrepancy that stood here is closed.

AW-01, the KV-cache prefix side channel. A 2025 academic paper found that KV-cache sharing, combined with longest-prefix-match scheduling in multi-tenant model serving, creates a return-order side channel: a local model using the same tokenizer can reconstruct another tenant's prompt token by token. Applicability to HIP is rated HIGH. The paper names shared physical hardware, colocation, as the main real-world obstacle to this attack, and an operator hub serving one neighborhood off one or two accelerators guarantees exactly that colocation; the paper also measured that the attack performs better on an underloaded accelerator, which an edge hub is by design. This is why edge colocation makes this specific attack surface worse, not better, against an intuition that a smaller, more local deployment is automatically safer. A further amplifier exists in the current system: every household is served from the same system-prompt template, which matches the paper's cheapest and highest-success scenario, a cloze-style extraction case measured at 99 percent success; an adversary household that knows the shared boilerplate can begin guessing at the first token where the prompts diverge, which in this deployment would be another household's private information.

AW-02, shared-silicon risk beyond the cache. Attention-masking defects in packed batches, shared logs and crash dumps, error paths that echo prompt content, and timing or contention side channels. A cable operator crossing this boundary between households, rather than between members of one household, crosses a legal category above the member-level boundary HIP already enforces. Not yet scoped to a fix. Open.

AW-03, no detection today. Nothing in the current harness or runtime watches for a cross-household fragment appearing in a reply; a successful exploit of AW-01 or AW-02 would be silent, unlike a refusal failure, which is visible. The proposed resolution is a hard-zero invariant class for cross-household contamination, using per-household canary facts, held separate from the existing member-isolation checks. Open.

AW-04, the limit of confidential computing at this layer. Confidential computing encrypts accelerator memory against the host, which gives operator-blind protection from the host as a whole. When one model instance serves many tenants, all of those tenants sit inside the same enclave together, protected collectively from the operator, not from each other. Separating tenant from tenant cryptographically at inference requires a dedicated model instance per tenant, which gives up the utilization that makes shared serving economical in the first place. This is recorded as an accepted limit. No fix is proposed, because none exists at the current economics; the limit is stated plainly instead.

AW-05, layered defense, in order. Layer one, structural: households do not hold raw inference API access; they speak to the assistant, and the orchestrator builds the prompt and sets every parameter, which breaks a precondition the AW-01 paper's attack requires. This is a boundary, not a wall, since anything that reaches the orchestrator's own inference client regains that control. Layer two: per-household cache scoping, the proposed resolution to AW-01 itself. Layer three: rate limiting against five usage signals the same paper measured, request volume, single-token candidate probing, candidate fan-out, oversized dummy batches, and a pattern designed to force cache eviction. Layer three is proposed, not yet implemented.

AW-06, detection signatures for KV-cache prompt extraction, richer than volume alone, specifying AW-05's layer three in full. Five signatures. Volume: the source paper's own user model is 40 requests per 3 hours per user; an extraction needs 1,500 to 4,800 requests per prompt, two to three orders of magnitude above household norms. A single-token output length set on candidate and dummy requests, to minimize the attacker's own memory strain; a household query always wants a full answer, so a stream of single-token-output requests is diagnostic on its own. Candidate fan-out: many requests sharing an identical prefix, differing only in the final token, submitted close together, the token-extraction primitive's own fingerprint and nearly impossible to produce by accident. Dummy batches: repeated batches of identical prompts, sized to exceed the maximum batch size, interleaved before and after the fan-out. The cache-flush pattern, the inverse signature: requests with unique leading tokens and maximum output length, sent to saturate memory and force eviction between extraction rounds. Proposed resolution, in order of precedence, the structural answer before the detection signatures: the source paper's third attack condition is that a client holds extensive control over request parameters and unrestricted dispatch; HIP's households do not hold raw inference API access, so that condition is broken architecturally, the same boundary AW-05's layer one already names, not by monitoring for it. Stated plainly, the same caveat AW-05 already carries: this is a boundary, not a wall. Anything that reaches the orchestrator's own inference client, a compromised edge process or a scripted device, regains that control, which is why the five signatures above remain worth having as defense in depth behind the structural boundary. Status: SPECIFIED, NOT BUILT.

## 7. Custodian position today

The strong claim. Operator-blind at rest is proven, on built code, today. The master key was destroyed under Bill's explicit, in-session authorization: backed up first, then its bytes overwritten with fresh random data, synced to disk, and unlinked, not a bare delete. Two proofs were run directly against all twelve facts that existed at the time. The negative proof: decryption attempted through the old master-key path fails 12 of 12, because no master key exists anywhere on disk. The positive proof: decryption of the same twelve facts through each fact's own legitimate class key succeeds 12 of 12, with zero master key present anywhere in the process. Two checks confirm no fact sealed under the old scheme remains and that no code path can produce one; a further check makes that a standing property enforced on every run; a successor check, built after the two original checks' own fault-injection twins were retired as no longer constructible, verifies that no master-key file exists and that any attempt to construct a fact under the old scheme raises an error rather than succeeding silently. Facts are sealed by class: each fact's own encryption key is wrapped to the reader roster for its scope, and the single key that once could unwrap every scope at once no longer exists to be compromised.

The narrow limit, stated in the same breath. At inference, the caller's own key unwraps a fact, and the local model holds that fact as plaintext in memory for the duration of the turn. An operator who compromised the running host during an active query for a given user could read that turn's data. Closing this gap requires confidential computing, which, per Section 3, is adopted infrastructure not yet integrated into HIP's inference path. The claim is exact and must stay exact: operator-blind at rest, not operator-blind at inference. The two are never the same sentence.

One further caveat on scope. The four write-time partition scopes that will govern where a newly written fact is sealed are ratified as a decision, per Section 2, but the requirement's own acceptance table has not yet been run, and the classifier that would assign new facts to those scopes automatically is unbuilt. The proof above covers the facts that existed under the crypto scheme already built at the time the master key was destroyed. It does not yet cover a fully automated write path for facts written from this point forward.

## 8. Target architecture at viable product

A four-tier deployment hierarchy is proposed in the Context and Interaction Architecture Proposal. It is not yet ratified; it is stated here as the target, not the built state.

Household: encrypted memory, household policy, and personalization weights, held privately, per household.

Edge or operator site: speech models, embeddings, a ranker, small reasoning models, and a shared meta-policy. One shared meta-policy may serve many sites at once, while each household beneath those sites keeps its own private local state; the site is the shared layer, the household is the private layer, and the two are never merged.

Operator core: model management, policy distribution, evaluation, training, telemetry, and the model registry.

Frontier: optional external reasoners, user-authorized services, and specialized APIs, reached only when a household or the operator explicitly authorizes it.

This hierarchy is where the two subjects separated in Section 6 meet. Routing most households to a shared-served model happens at the edge or operator site, which is Case 1 economics. A tenant that needs dedicated silicon escalates toward the operator core or beyond, which is Case 2. Case 3, shared silicon among tenant-owned models, is not offered at any tier.

Section 3 already named the infrastructure vendors HIP rents from by layer: foundation models, speech models, embedding and reranking models, graph and vector stores, and confidential-computing hardware. This section covers the application-layer competitors named in the ecosystem analysis, and where HIP does and does not compete.

HIP's claimed ownership is four layers that compound rather than commoditize: the routing cascade, for margin; the injection contract, for the context moat; the operator-blind architecture, for the liability moat; and the governance harness, for the compliance moat. Everything else named in this section and in Section 3 is rented, because it commoditizes.

## 10. Long vision (positioning ratified 2026-07-27, DISPATCH 41)

The positioning below, the thesis and the three positions that follow the generation list, is ratified 2026-07-27. The six-generation roadmap itself remains proposed, not built, exactly as the next paragraph already states. The observation-and-perception custody positions that position 1 cross-references are themselves also ratified as of 2026-07-27 (DISPATCH 43), with named exceptions, tracked in full in REQ_PARTITION_CUSTODY.

The context manager's own roadmap, as proposed and not yet ratified in the Context and Interaction Architecture Proposal, runs six generations.

Generation 1: rules plus vector similarity.
Generation 2: rules plus graph plus temporal filters plus ranking. The built system described in Section 2 sits at this generation today.
Generation 3: learned ranking. Not pursued. The three preconditions in Section 4 remain two-of-three MET (the output invariant, the prompt-to-record fidelity invariant), the third, learner training-signal isolation, NOT MET; the choice of whether to adopt this track at all is no longer undecided, it is ratified against: retrieval stays rule-based indefinitely, per Section 4.
Generation 4: household-personalized ranking.
Generation 5: counterfactual context optimization. This is where the proposed evaluation methods named in Section 5, counterfactual ablation, context lift, and dead-token rate, would apply, once they exist as harness checks rather than proposal text.
Generation 6: predictive context assembly. At this generation the system retrieves information because it predicts the next reasoning step will need it, rather than because the user mentioned it. The source document describes this as closer to household intelligence than conventional retrieval.

Vertical depth, world modeling, and multi-modal input are not separate bets. Each is the same governed substrate extended: new input classes in, predictive structure over it, domain context packs on top. The models involved commoditize. The substrate does not.

Three positions follow from this thesis, ratified 2026-07-27.

Multi-modal input is perception. It is not a separate track. It is an input class. A camera frame or a sensor reading mints a derived, sealed fact into the same governed store, under the observation-and-perception custody positions recorded in REQ_PARTITION_CUSTODY's "Observation-and-perception custody" section, ratified 2026-07-27 with named exceptions: sealed to the right audience, process-and-discard so frames are never retained, and corroborate-never-confirm so a model with an error rate cannot mint CONFIRMED. Perception input is governed on day one. It is not retrofitted afterward.

World model means the graph made predictive. It is not a larger neural network. It is the household's bitemporal fact graph, made predictive with time and causal structure over it: who is home when, what supersedes what, what usually follows what. This is the moat category, because it trains on the governed substrate. It sits behind the same learner-signal-isolation gate as every other learning track named in Section 4. It is the destination the context manager's later generations point toward, Generation 6 above named specifically, not a separate ambition beside them.

Verticality lives in governed context. HIP does not fine-tune or host domain-specific models. Care, finance and the rest are expressed in the attribute taxonomy, the write rules, the scopes and the precedence rules that already govern the household graph. The models underneath stay commodity and swappable. This is the thesis applied: a care-specific model commoditizes like any model. A care-specific governed context compounds.

Ordering, stated plainly. Perception inputs enter when the custody positions above ratify. The predictive layer enters after the learning substrate exists, the same gate Section 4 already places on Generation 3. Vertical context packs can begin at any time, because they are rules and taxonomy, not models, and carry none of the other two tracks' preconditions.
